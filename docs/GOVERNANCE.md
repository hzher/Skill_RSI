# 项目治理与权限约定

## 项目共同目标

围绕 Claude Code、Codex、DSH，形成持续循环：

**真实执行 → 有效、可复用的 trajectory → context/memory skills → 后续任务使用与反馈 → 持续迭代。**

轨迹质量和 skills 迭代共同构成核心交付；模型参数训练与之并行。任务由成员认领，不在初始化文档中替成员承诺模块职责或工期。

## 角色与权限边界

| 角色 | 团队职责 | 权限说明 |
|---|---|---|
| 仓库所有者 `@hzher` | 管理仓库设置、可见性与协作者访问 | 个人账号仓库的所有者 |
| 项目负责人 `@sheepyedu` | 协调项目、组织审核、修改并合并主线变更 | 协作者邀请已发送，待接受后获得读写及 PR 合并权限；不是 GitHub Admin |
| 维护者 | 组织共同目标、处理合并、协调资源和验收 | 所有者与已获实际写权限的负责人按分工执行 |
| 贡献成员 | 认领任务、在个人分支提交、参与交叉审核 | GitHub 账号及访问权限待确认，不视为已获授权 |

本仓库位于个人账号名下。协作者访问与组织仓库的细分角色不能混用；文档中的“维护者”首先表示团队分工，不自动对应一个独立的 GitHub 权限等级。

成员不改他人分支属于团队约定。`master` 的 PR、禁止强推和删除等已由保护规则强制执行；个人仓库无法另授 Admin，也无法仅凭分支名隔离成员写入权限。

## 合并与分支管理约定

- 改动通过 PR 进入 `master`；初始化时批准数为 0，仍需处理讨论并保留验证。其他审核成员接受邀请后，再启用至少一位非作者批准；维护者或具备写权限的负责人 Squash merge。
- 长期个人分支使用 merge 同步 `master`；禁止 rebase 和强推已共享分支。
- 不自动删除长期个人分支，不强推或删除共同基线。
- 当前阶段不配置不存在的 CI 为必需检查，也不启用唯一 CODEOWNER 的强制审核。

完整流程见 [CONTRIBUTING](../CONTRIBUTING.md)。

## 决策与资源协作

每项任务在 Issue 中指定一位直接负责人。目标、接口、轨迹质量标准、skill 验收或实验拆分变更，记录原因、影响和决定；不要仅在个人分支或临时聊天中保留结论。

GPU、API、运行机器和任务环境统一登记使用人、用途、预算、使用时段及结果位置。每两天简短对齐交付和阻塞，汇报基于运行证据与实际认领；不在仓库中提交内部人员评价或未经授权的会议材料。
