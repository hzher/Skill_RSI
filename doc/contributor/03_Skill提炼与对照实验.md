# 03　从任务历史发现策略，验证扩展包

开发者向 Part 2 提交的是一条**能被证据推翻的策略**。例如，遇到重复查询时先复用旧结论，如果来源版本发生变化就重新核验。Part 2 可以调用大模型阅读 Part 1 的记录或用户提供的历史，提出算法，生成代码、配置或 Skill，再交给独立任务验证。用户通过宿主安装已发布的包，发现所用的大模型和私有轨迹都留在研发侧。[总体架构](01_总体方案与架构.md) · [轨迹与制品字段](02_轨迹数据契约.md)

## 准备一个可分析的窗口

| 数据来源 | 可以交给提炼器什么 | 还需要核对什么 |
|---|---|---|
| 用户选定的本地会话或任务历史 | 当时的目标、工具动作、来源版本、用户后续更正及测试结果 | 单有对话时，能断定用户纠正过单位。缺少实际模型输入时，约束是否在压缩中丢失保留为未知。 |
| 正在运行的宿主 | 检查点之前已落盘的事件、项目和会话血缘、当前版本及已公开反馈 | 先封存前缀，再分析。迟到的反馈另记修订，历史回填与实时采集遇到同一事件只算一次。 |
| benchmark 或合成任务 | 可重复的初态、公开任务观察、由评测器单独保管的结果 | 发现前按项目、实例和共享会话祖先划分开发与留出组。同一实例换宿主仍归同一组。 |

用户按项目选择可用于发现的字段。提炼器只读这些字段，保存所读窗口、来源引用及摘要。决策前可见的内容和事后诊断反馈分开，隐藏答案保留在评测器。对外共享的包使用合成样例。既有原型支持按字段、事件与摘要核对提炼输入。[本地原型的字段投影](../../../Skill_RSI_hzh/skill_discovery/inputs.py) · [数据和宿主如何接入](06_数据与宿主接入.md)

**跨宿主比较时，先对齐能回答的问题。** 例如发现模型提出“新版约束在恢复后没有送到主请求”。若 DSH 只剩 SDK 参数，或 Claude Code 只存了压缩快照，就把这两次运行计入“后续主请求未知”。在 Codex 能还原完整逻辑输入，或在 Claude Code 能核对对应网关出站请求时，分别报告各层可检查的调用数和命中数。要判断哪种策略让换算更准，三端都要另外检查下一步的真实参数或提交结果。[三端取证例子](02_轨迹数据契约.md#三种宿主的原始文件)

## 从成功和失败的差异中提议算法

1. **找到分歧。** 对同类任务各选一次成功、一次失败或返工，再加入一次没有介入也顺利完成的机会。要求发现模型指出第一次差异、引用读过的证据，并列出其他可能解释。
2. **写成候选。** 说明适用对象、触发时机、输入、动作、跳过条件、预算和回退。已有提炼器按阅读、比较、提议、泛化四步工作，可以生成 `SKILL.md`，也可以在证据不足时返回零候选。[模型调用](../../../Skill_RSI_hzh/skill_discovery/teacher.py) · [候选渲染](../../../Skill_RSI_hzh/skill_discovery/extract.py)
3. **交付可测试的包。** 按算法需要选择 Skill、MCP 工具、hook、插件、受控网关或多节点中间件。冻结 `component_id`、版本、载体与 `artifact_digest`，列明宿主能在哪个节点读写、如何停用，再附带应触发和应跳过的例子。

| 首版候选 | 开发时可以用的例子 | 能推翻候选的情况 |
|---|---|---|
| `tool-result-view` 工具结果按需展开 | 长日志保留有版本的原件，先显示出错行和可展开的引用。需要更多证据时按原文行号读回。 | 关键错误藏在最后一行；原文随来源更新而变化。引用应读到对应版本，无法提供可靠原文时走原生输出。 |
| `constraint-check` 旧约束核验 | 报表用秒，旧接口给毫秒。恢复时若下一步确实要换算，就核对接口修订。来源未变可复用，已变则只查新单位。 | 另一接口发生改动，或当前输入已有核实过的新单位。此时多做一次检索会增加成本，应当跳过。 |

两个包分别安装、按项目绑定。`shadow` 只计算本包本来会做的动作，检查拟触发和回退次数。`suggest` 登记展示与采纳，`apply` 以宿主实际回执确认动作。项目是否启用 Part 1 的 `observe` 采集由用户单独选择。单独停用展开包后，下一生效边界起新结果恢复原生展示，保留期内的旧引用仍可读，核验包能继续直接核对原生来源。[绑定与回执](02_轨迹数据契约.md)

## 独立验收怎样设计

先锁定包摘要、宿主与模型版本、预算、初态、主指标和可接受的退化，再运行没有参加发现的完整任务。每组使用隔离工作区和相同种子。能够恢复中间状态时，可先在错误发生前对照执行几个候选，确认第一项行动有没有改变。

| 比较 | 实验条件 | 回答的问题 |
|---|---|---|
| 谁来管理工具视图 | 关闭核验包，比较原生、固定规则遮盖旧结果、模型自行聚焦和恢复、冻结策略自动选择。后两组拥有相同操作与预算。 | 简单规则够用吗？让策略自动选择是否减少重读，同时保留关键事实？ |
| 两个包各自的贡献 | 在同一适配器上比较两包均关、只开展开、只开核验、两包同开。两包均关再与纯原生比较适配器开销。 | 两个独立包各带来多少收益？组合后会不会多查一次或用错旧版本？ |

每组分别报**恢复后的失败率、首个关键动作正确率、完整任务通过率、重复读取及全程成本**。对原始分组报告配对数、每对差值和不确定性，保留未触发、漏载、超时和缺分，并注明原因。对外判定采用 `validated_in_scope`（在注明范围有效）、`rejected`（低于预设目标）或 `inconclusive`（证据不足）。候选发布报告附宿主实际加载和应用回执，并注明用户可以采用的版本与回退方式。[已有冻结与验证程序](../../../Skill_RSI_hzh/skill_discovery/validate.py)

已有 DSH 试验展示了为什么要同时看任务结果与开销。在 `cohort_studies` 的同一段 12 个实例里，常驻 Skill 让成功数从 5 变为 8，原生模型调用也从 70 变为 101。这 12 个实例共享一条连续轨迹。该记录可用于验收报告的字段与计算口径；首版两个包的实际效果仍需独立测试。[原始汇总](../../../Skill_RSI_hzh/results/skill-gate-pilot-20261119-200011/summary.json)
