# 02　轨迹数据契约

开发宿主适配器时，要能回答一个具体问题：助手做出下一次决定之前，能看到哪个版本的证据，后来做了什么？Part 1 留下带来源的事实。Part 2 从获准的历史窗口提出策略，在独立任务上验证，再交付可安装的扩展包。

**已有格式**是相邻原型仓可读写的 `SkillRSI-CTX-v1`。下文的事件扩展、策略包、项目绑定和在线回执是主项目待实现的契约。历史归档保持原有字节和引用，新增记录通过版本和摘要关联旧包。[现有数据类型](../../../Skill_RSI_hzh/evidence/schema.py) · [参考写入器](../../../Skill_RSI_hzh/evidence/build.py)

## 读取一份已有归档

### 标准归档的文件树

从 `batch_index.json` 选一次运行，按它的 `run_id` 打开对应目录。一批可以有多次运行，一次运行可以跨多个任务实例。下面是参考写入器的默认布局，尖括号中的部分用实际值替换。

```text
derived/skill-rsi-v1/
├── batch_index.json                       # 批次入口，列出各次运行
└── runs/
    └── <run_id>/
        ├── manifest.json                  # 谁运行、用了什么配置
        ├── events.jsonl                   # 发生了什么
        ├── requests/
        │   └── index.jsonl                # 每次模型调用有哪些可核对的证据
        ├── trajectory.ctx.json            # 会话、分段与调用的关系
        ├── context_episodes.jsonl         # 压缩、恢复等上下文变化窗口
        ├── scores.jsonl                   # 实例与指标的评分记录
        ├── artifacts.json                 # 原件和公共文件的校验清单
        ├── quality.json                   # 证据覆盖到了哪一层
        ├── raw/<harness>/native/<sha256>/<原文件名>  # 封存的宿主原件，按需出现
        └── snapshots/objects/<sha256>               # 封存的记忆快照，按需出现
```

**交付规则。** 每次运行都要交付表中的八个文件。四个 `.json` 文件各存一个 JSON 对象。四个 `.jsonl` 文件按行存对象，都允许零行。例如没有评分器时，保留空的 `scores.jsonl`，表示没有评分记录。少交文件会导致校验失败。

| 文件 | 读到什么 |
|---|---|
| `manifest.json` | 宿主、执行身份、配置、来源指纹和采集能力 |
| `events.jsonl` | 原生事件、工具和环境动作、相应回执。用 `run_id + event_id` 定位一条记录 |
| `requests/index.jsonl` | 逻辑调用、已观察到的发送、请求与响应引用，以及最终输入缺失的原因 |
| `trajectory.ctx.json` | 会话 → 上下文分段 → 调用步骤，含分支、恢复及上下文变化的来源 |
| `context_episodes.jsonl` | 与记忆或上下文相关的事件窗口、标签及证据强度 |
| `scores.jsonl` | 每个实例、每项指标的原始分数、评分状态及评分器版本 |
| `artifacts.json` | 原件清单、字节数、摘要和记忆对象版本 |
| `quality.json` | 可观察范围、缺失或歧义、用途资格及统计分母 |

**定位原文。** 每条原文引用用 `source_root` 和 `path` 找文件，用 `bytes` 和 `sha256` 核对原始字节，用 `locator` 定位整文件、从 1 开始的物理行号或 JSON Pointer。`payload_layer` 说明读到的是哪一层证据。`artifacts.json` 列出其余七份公共文件和引用的原件，它自身的摘要存在批次索引的 `runs[].artifact_manifest` 中。同一原件可被多个事件引用，两次实际工具执行仍各有身份。[引用解析](../../../Skill_RSI_hzh/evidence/archive.py) · [完整性验证](../../../Skill_RSI_hzh/evidence/verify.py)

**复制到另一台机器。** 先看 `quality.json` 的 `sources_sealed`。构建时加 `--seal` 会把运行引用的原件复制到上述两个按需出现的目录，路径从本次运行目录解析（`source_root=run`）。未封存的原件仍从原始批次解析（`source_root=batch`）。迁移未封存归档时需一并保留原始批次，校验时用 `--batch-dir` 指向它。

**可执行示例。** 从 `Sklii_RSI_master/` 根目录运行，使用已装相邻原型依赖的 Python 环境。命令只读归档，预期有 `run_count = 5`、`integrity = verified`。

```sh
(cd ../Skill_RSI_hzh && python -B -m evidence verify results/v2-db-contract-v1-control/derived/skill-rsi-v1)
```

这批数据的 `61dfed3367d04488a0c524fc86493217` 有 131 条请求索引，其中能核验最终输入的调用为 0。实现 reader 时应输出“最终输入未知”，即使每条请求都留有可读的原生参数。[真实批次索引](../../../Skill_RSI_hzh/results/v2-db-contract-v1-control/derived/skill-rsi-v1/batch_index.json) · [该运行的质量记录](../../../Skill_RSI_hzh/results/v2-db-contract-v1-control/derived/skill-rsi-v1/runs/61dfed3367d04488a0c524fc86493217/quality.json)

第一条请求的字段节选如下。`logical_call_id` 可用来查找此次调用，`native_options` 表示记录器看到宿主准备的参数。物理发送和最终输入各自有缺证原因。

```json
{
  "logical_call_id": "6b7f2b9d-e88a-4754-b3c2-b3c92e807650",
  "request_evidence_kind": "native_options",
  "attempt_id": null,
  "actual_context_ref": null,
  "missing_reasons": ["physical_send_attempt_unobserved", "effective_endpoint_input_unverified"]
}
```

## 输入格式兼容表

| 手里的数据 | 接入方式 | 可以确认什么 |
|---|---|---|
| 带 `batch_index.json` 的标准归档 | **已有，可直接校验。** 从索引读 `schema_version`，当前识别 `SkillRSI-CTX-v1`。可自定义归档目录名。 | 查看每次运行的 `quality.json`，了解哪些事件、请求、评分有证据。 |
| DSH 原始批次 | **已有，先转换。** 读取 `checkpoints/<task>/attempts/<job>/<attempt>/manifest.json` 及其声明的轨迹，也识别旧检查点，如 `checkpoints/<task>/run-0.json.gz`。按实际采集情况关联 `native/<task>/<runtime_id>/` 下的请求和会话记录。 | 可以保留任务重跑、请求和会话的来源。具体能否还原模型输入取决于此次采集。 |
| CL-Bench 导出的 Claude Code 或 Codex 轨迹 | **已有，先转换。** 选择对应宿主，以兼容的 `.json` 或 `.json.gz` 轨迹对象为入口，读取内嵌事件或配套的会话 JSONL。 | 能定位导出物记录的对话与工具事件。单独一份同名 JSONL 不足以按这个入口导入。 |
| 本机 Codex rollout trace | **可离线还原，公共导入待接。** 对支持的版本使用配套 reducer 生成 `state.json`。普通 CLI 或 MCP 历史也可供补录。 | 能沿主线程、turn、调用 ID 核对逻辑请求里有哪些输入项。传输与服务端处理各看相应回执。[Codex 原生夹具](adapters_doc/codex/原生轨迹离线验收.md) |
| Claude Code 的 transcript、压缩快照或网关记录 | **原型能留存，公共导入待接。** 导入时分别识别会话快照、Messages 入站和实际上游协议。 | 比较两侧快照可确认文件发生了什么变化。要确认内容进入后续主请求，需要找到该步骤对应的请求和交付边界。[Claude Code 方案](adapters_doc/claude_code/README.md) |
| 自定义 JSONL，如团队工具导出的事件表 | **规划用字段映射接入。** 当差异仅在列名和类型名时，提交映射及一行样例，给每条事件保留稳定标识和原始行号。 | 可按已声明的字段还原顺序、角色和事件类型。缺少请求正文时，模型输入仍未知。 |
| 纯文本 `.txt`、Markdown 聊天导出 | **需文本读取器，属规划入口。** 保留原文件，以文件摘要和原始行号引用片段，只映射文本里明确出现的角色和时间。 | 例如第 12 行写着“单位改为秒”，可引用这行作为修订线索。后续模型是否读到、任务是否通过，都留作未知。 |

DSH 和 CL-Bench 的现有入口见各自的读取器。贡献本机日志或文本读取器时，可从接入文档中的映射示例开始。[DSH 读取器](../../../Skill_RSI_hzh/evidence/dsh.py) · [Claude Code / Codex 的 CL-Bench 读取器](../../../Skill_RSI_hzh/adapters/native.py) · [本地数据接入示例](06_数据与宿主接入.md)

**编码与压缩。** 交换文件使用 UTF-8。JSONL 每个非空行存一个完整对象，空行跳过，引用仍按原文件的物理行号计数。参考读取器可读取其支持的单对象 `.json.gz`，校验摘要时使用压缩文件的原始字节。`.jsonl.gz` 没有直接读取入口，接入时需要能处理该压缩格式的读取器。[文件读取规则](../../../Skill_RSI_hzh/evidence/archive.py)

**读到未知或损坏的数据。** 索引版本无法识别、运行中记录的版本与契约不符、公共文件缺失、摘要不符或引用定位失败，归档校验均应失败。保存原件和错误位置再做转换。校验通过后，仍可能遇到未观测的调用或分数，按缺证原因标为“未知”。例如空的评分文件与一条数值为 `0` 的评分记录有不同含义。

## 三种宿主的原始文件

下面列出各宿主参考实现中的典型文件。三棵树的根目录彼此独立，具体文件随采集配置和运行进度出现。DSH 的受支持批次已有公共导出器。Claude Code 长链原件和 Codex 原生 bundle 按下表设计映射，原件路径、摘要和定位随公共记录保存。

```text
<DSH 原始批次>/
├── checkpoints/<task>/attempts/<job>/<attempt>/manifest.json
└── native/<task>/<runtime_id>/
    ├── capture/calls.jsonl                  # 调用开始、结束及可用的载荷引用
    ├── request-*.json                       # 宿主准备的 SDK 参数
    └── sessions/<项目>/<会话>/session.v4.jsonl

<Claude Code 长链原型的运行目录>/
├── workspace/.agent/context-events/<时间戳>-<hook 名>/
│   ├── event.json                           # hook 事件与已保存文件的摘要
│   ├── transcript.jsonl                     # 源 transcript 存在时复制
│   └── notes/<相对路径>                     # 按当时可见的笔记保存
└── upstream/<请求序号>/                     # 已配置 Chat 网关，文件随阶段产生
    ├── request.messages.raw                 # 入站 Messages 请求
    ├── request.raw                          # 转换后准备发往上游的请求
    ├── response.raw                         # 观测到的上游响应字节
    └── receipt.json                         # 转发、完成或失败状态

<Codex rollout trace bundle>/                # 此例使用 trace schema 2
├── manifest.json                           # trace、rollout、根线程标识
├── trace.jsonl                             # 有序原生事件
├── payloads/                               # 事件引用的请求、响应或工具正文
└── state.json                              # 匹配版本的 reducer 生成
```

以“工具读回了新版单位，助手下一步仍用了旧值”为例。先在 `events.jsonl` 登记工具返回及来源，再查下一次**主任务调用**。三端各有一条能核对的路径。

| 从哪个原生标识追查 | 公共轨迹应当怎样记 |
|---|---|
| **DSH** · 在同一 session 和 query 内，用原生调用 ID 对上调用记录和 SDK 参数。 | `requests/index.jsonl` 可记 `request_evidence_kind=native_options`。只有参数原件时，最终输入引用留空，缺口写入质量记录。[DSH 请求回查例子](adapters_doc/dsh/README.md) |
| **Claude Code** · 用 `tool_use.id` 与 `tool_result.tool_use_id` 配对，再按会话和请求范围查后续请求。 | 快照进原件清单，压缩边界进上下文窗口。核对出站正文、转发回执和 HTTP 状态。`forwarded=true` 只表明已尝试转发；上游是否响应要另看 HTTP 回执。只有笔记或 hook 回执时，后续主请求仍未知。[Claude Code 文件映射](adapters_doc/claude_code/README.md) |
| **Codex** · 从根线程目标 turn 的 `inference_calls` 查有序 `request_item_ids`，用模型侧调用 ID 与结果正文配对。 | 能还原的内容记为该次逻辑调用的输入。WebSocket 增量需要可核对的前缀。只有子线程收到或只有 MCP 返回时，父线程主请求仍未知。缺失载荷、未闭合等情况在质量记录中分开说明。[Codex 还原与映射](adapters_doc/codex/README.md) |

后续动作是否沿用旧单位，要从下一次工具参数或提交物取证。任务是否完成，再读本地测试或 benchmark 的原生结果。Part 2 可用这几层证据区分“取回了旧版本”“新版已进入逻辑输入但操作仍错”和“现有记录不足以定位”。

## 新适配器交付什么

本地对话、已导出的任务目录和在线宿主走相同的事件语义。列名不同可以映射，需要解析原生线程或工具协议时由宿主适配器提供解码。Benchmark 另行提供任务和评分器。无评分器的项目可以引用测试结果或用户纠正，注明来源。开发者可独立贡献任一入口。[数据与宿主接入](06_数据与宿主接入.md)

| 记录 | 至少保留 | 开发者要核对什么 |
|---|---|---|
| 来源与事件 | `schema_version, project_id, run_id, event_id, source_id, cursor, seq, type, visibility, source_ref` | 在来源命名空间用原生 ID 或不可变分段与位置认同一事件。历史回填和实时订阅可以对账。保留宿主、版本、原时间以及能确认的线程或父分支。旧 v1 用 `raw_ref` 指向原文。 |
| 介入机会与可见范围 | `opportunity_id, boundary_ref, target_object, visible_state_ref`，另记窗口范围、采样规则、丢失区间和关闭状态 | 对恢复、压缩、重复读和版本修订记录当时可见的证据。无策略、主动跳过、未知及失败也入样；报告机会总数与可观测数。 |
| 内容流转 | `opportunity_id, artifact_version, stage, layer, call_ref, observation, evidence_ref` | 分别核对工具返回、写进历史、进入决策前的目标主请求及后续动作吻合。每一层记“证实有／证实无／未知／不适用”。断言缺失需要完整边界与可核对的内容。 |
| 事实与反馈 | `project_id, object_id, version, parent_version, source_refs, validity`。反馈另记 `kind, value, unit, source_ref` | 新修订引用父版本。用户采纳、宿主投递成功和任务通过分别给回执。分数保留指标、方向、评分器版本，未知值用 `null` 和缺失原因。 |

`logical_call_id` 表示一次逻辑模型调用，`attempt_id` 表示一次可证实的实际发送，`job_attempt_id` 表示整项任务重跑。存原件和事件成功后再推进来源游标。把导入与订阅中重复出现的事件计一次，同时保留各自出处。同一工具操作在 transcript、MCP 和网关留下的收据，按可核对的调用 ID 或操作键对账。仅有相同参数或相近时间时保留关联未知。

## 从记录到可供发现的窗口

Part 1 冻结 `window_id, revision, lineage_id, split, run_id, event_refs, visibility, allowed_use`。窗口里的决策前输入与事后观察分别标注，迟到反馈形成新修订。Part 2 可以分析成功、失败和无需介入的窗口，返回实际读过的事件引用、候选算法、反例及待验证的收益。只有旧对话时同样可以提出候选，缺失的工具和主请求边界保留未知。[提炼与对照实验](03_Skill提炼与对照实验.md)

- **拆分**在切窗之前完成。按项目、任务实例及共有会话祖先分组，同一初态的兄弟分支和同源的跨宿主副本进入同一组。将评估留出组与发现、调参及训练数据隔离。
- **授权**按来源、用途、字段和版本投影。已有提炼器使用 `development_groups`、`holdout_groups` 和 `payload_allowlist`，涉及正文的批准精确到 `run_id, event_id, field, sha256`。可见性说明技术上能读多少，用途授权决定可以交给谁。提炼和执行输入排除标准答案、裁判私有状态、账户密钥及未经授权的正文。[现有输入投影](../../../Skill_RSI_hzh/skill_discovery/inputs.py)
- **训练**另行交接。获准用于提炼的记录要用于更新模型权重时，需要相应的训练用途记录和训练仓能复算的样本。原生成绩留在评估侧，训练需要的奖励走独立接口。[离线训练交接](04_离线训练交接.md)

## 从发布清单到宿主回执

| 对象 | 字段与行为 |
|---|---|
| 扩展包清单 | `component_id, version, form, entrypoint, files, required_capabilities, scope, trigger, action, budget, fallback`。声明支持的宿主与模式、读写目标和状态格式。每个文件校验 SHA-256；`artifact_digest` 固定实现文件、行为配置与依赖版本，摘要自身及事后报告从计算中排除。 |
| 项目绑定 | `(project_id, host, component_id)` 唯一确定绑定。`version, form, artifact_digest` 锁定执行内容。`enabled, mode, binding_revision` 表示用户选择。适配器用 `effective_boundary_ref` 报告真正生效的位置，需要重启时先记为待生效。 |
| 决策与回执 | 决策记录 `decision_id, trigger_ref, component_id, artifact_digest, binding_revision, mode, proposed_action, reason, operation_key`，附项目、宿主与版本。写操作先登记意图，之后由宿主记录实际 `stage, status, receipt_ref` 及失败原因。操作键区分项目、宿主、运行、触发事件、制品摘要和动作序号。 |

`observe` 单独控制项目的 Part 1 采集，零个扩展包也能记录任务。每个包另选模式：`shadow` 在隔离状态内试算，对宿主的展示和写入均为零；`suggest` 展示建议，采纳与执行各自记账；`apply` 校验能力、权限与输入版本后提交动作。项目只使用成品时，运行所需的本地回执可独立于研究轨迹保存。

**合成案例。** 项目 A 在 DSH 同时绑定 `tool-result-view` 和 `constraint-check`。报表旧接口 v3 返回毫秒，新接口 v4 返回秒。下表中 `e1` 到 `e4` 是同一 run 内的源事件标识，可直接用作适配器夹具的断言。

| 已观察到的事件 | 回执或应有结果 |
|---|---|
| `e1` 工具读取 v4 说明，长输出含 `unit=s` | 展开包以 `apply` 保存有版本的原件，返回短视图和引用。记录原件版本、可读范围和实际投递层。 |
| `e2` 恢复任务，旧公式依赖 v3 | 核验包处于 `shadow`，可登记“应查 v4”，真实工具执行次数为 0。此时展开包仍按自己的模式运行。 |
| `e3` 核验包切到 `apply` 后，下一次动作仍依赖旧单位 | 以当时可见的输入重新决策。若工具返回 v4 的 `s`，工具层可标“证实有”。缺少主请求证据时，该层标“未知”。重复收到 `e3` 时复用同一操作回执。 |
| `e4` 在宿主已确认的边界后，展开包停用，再读取一份日志 | 新结果按原生方式展示，旧引用在项目原有权限和保留期内可读。核验包仍可从宿主来源工作。最终换算是否正确须另读任务断言。 |

## 兼容与故障验收

1. **只读导入。** 重跑同一批、重叠消费两个游标及断点续接后，核对事件数、实际发送次数和外部副作用次数。导入不会触发真实工具。遇到未知主版本时报告协议与定位，保留原件。
2. **并发与重试。** 写入受管状态先核对父版本。两个包在同一阶段争写相同目标时，对已知冲突拒绝此次绑定变更；运行时才发现则跳过冲突写入。非幂等动作超时且结果未知时先对账，在途回执仍关联原绑定修订。
3. **证据与权限。** 拿走请求原件后，“进入主请求”应为未知。改动原件一个字节应导致验证失败。修改隐藏答案只应改变评测结果。跨项目引用及超出许可的正文不能进入提炼输入。
4. **兼容性。** 新增窗口、绑定或诊断字段发布为版本化扩展并引用旧包摘要。改变字段单位、身份或评分语义时提升协议主版本，交付转换和不可恢复字段说明。比较迁移前后的运行、请求、评分、缺证及用途分布。[分工与 PR 规范](05_开发分工与PR规范.md)
